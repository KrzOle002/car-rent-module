# Car Rent Module

A small car rental system written in plain Java 21 for a technical assessment.
You can reserve a car of a given type (Sedan, SUV or Van) from a chosen date and time
for a number of days. Each type has a limited number of cars.

## How to run

You need Java 21 and Maven.

```
mvn test
```

There is no UI or API. The tests are the way to see the system working.

## What is where

```
org.krzole.carrent
├── model/        the things the system works with
│   ├── enums/CarType      SEDAN, SUV, VAN
│   ├── Car                one physical car (generated id + VIN + type)
│   ├── RentPeriod         start date/time + number of days
│   ├── Reservation        who booked which car and when
│   ├── Fleet              all cars the company owns, grouped by type
│   └── CarSchedule        the bookings of one car
├── service/      what the system does
│   ├── CarRentService     reserve, cancel, check availability
│   └── AllocationStrategy decides which free car to give out
└── exception/    business errors
```

## How the requirements are covered

- **Reserve a car of a type, at a date and time, for N days** – `CarRentService.reserve(...)`.
- **Three car types** – the `CarType` enum.
- **Limited number of cars per type** – the `Fleet` holds real cars, so the limit is simply
  how many cars of a type it has. When all of them are busy, `reserve` throws
  `NoCarAvailableException`.
- **Unit tests prove it** – 35 tests. `CarRentServiceTest` covers the requirements directly.

## Decisions I made

**Plain Java, no Spring or database.**
The task asks for a simulated system built with object-oriented principles and says to focus
on the non-trivial parts, not on infrastructure. So I spent the time on the booking rules,
thread safety and tests. `CarRentService` doesn't depend on any framework, so it could be put
behind a REST controller later without changes.

**A reservation gets a specific car, not just a type.**
The customer asks for "an SUV", but the system assigns a concrete car. Checking availability
then becomes a simple question: is this car free in this period? It also matches real life,
because the customer drives away in one specific car.

**Periods are half-open: `[start, start + days)`.**
A car returned at 10:00 can be rented again from 10:00. Without this, back-to-back rentals
would be refused for no reason. There are tests for both edges.

**Two reservations at the same time can't get the same car.**
"Check if a car is free, then book it" is a race condition: two people could both see the
last SUV as free and both book it. `CarRentService` uses one lock per car type, so checking
and booking happen together. Different types don't block each other.
`CarRentServiceConcurrencyTest` starts 32 threads at once against 3 SUVs and checks that
exactly 3 bookings succeed, each with a different car. If you remove the lock, it fails.

**Which car to give out is a separate strategy.**
Picking a car (first free one, least used, best fit) is a business rule that may change, so it
lives in `AllocationStrategy`. The default takes the first free car. The service still checks
the strategy's choice, so a buggy strategy can't cause a double booking.

**Cars have a generated `id` and a `VIN`.**
The `id` is generated by a thread-safe counter, the way a database would do it, and cars are
compared by it. The VIN is the real-world identifier; the fleet rejects duplicate VINs.

**The current time comes from an injected `Clock`.**
Reservations in the past are rejected. Tests use a fixed clock, so they don't depend on the
real date.

## Known limitations

- **Everything is in memory.** Reservations are lost when the program stops.
- **Works in one JVM only.** The locks don't help if several copies of the service run at once.
  With a database I would let the database prevent overlaps, for example with an exclusion
  constraint in PostgreSQL on car and time range.
- **Cars are not reshuffled.** Once a reservation gets a car, it stays on that car. In rare cases
  a request is refused even though it would fit if existing bookings were moved between cars of
  the same type. A smarter `AllocationStrategy` could handle that.
- **No time zones.** `LocalDateTime` assumes one location.
- **Whole days only**, as the task describes.
- **The fleet is fixed** once the service starts. Adding cars at runtime is not supported.
- **Out of scope:** prices, customer accounts, changing a reservation, pick-up and return, REST API.
